# T1.4: profile and optimize the search kernel

- **Command:** `modal run modal_app.py::profile_search` (profiling, on the pinned A100-40GB; `--ncu/--no-ncu`, `--micro/--no-micro`)
- **Commits:** profile `c19fa26`; "before" kernels built from `a2b0d86` (Barrett); "after" kernels `909ef4e` (Montgomery and launch bounds)
- **GPU:** NVIDIA A100-SXM4-40GB, 108 SMs, SM clock 1.41 GHz, HBM 1215 MHz on a 5120-bit bus, 1,555 GB/s peak. The oracle tests ran on the A10.
- **CUDA:** 12.6.3 image, nvcc 12.6.85, sm_80 for the benchmark
- **OpenFHE:** v1.6.1 (pinned image)
- **Parameter set:** `m0_depth2`: ring dimension 16384, 3 towers of 60/50/50 bits, so 49,152 words per polynomial. Benchmark moduli are freshly found NTT-friendly primes of those sizes; timing does not depend on values.
- **Timing:** kernel-only CUDA events, median of 11 runs after 3 warm-ups. Before and after share one harness; compare only those rows, since the T0.4 and T0.7 files used different methods. Blocks: 64, 32 and 16 for d = 384, 768 and 1536 (19.3 GB of stored data).

## Conclusion

**Montgomery multiplication plus an occupancy fix makes the T0.4 search kernel 1.49x to 1.54x faster, with every output word still exact.** The kernel was limited by the instruction count and dependency latency of 64-bit Barrett reduction, and by its 25% occupancy ceiling, not by memory. It now runs at 88% of the memory-only floor for its access pattern, at d = 384, so further gains need a different access pattern or smaller words.

## What limits the kernel (before optimization)

**Nsight Compute on the T0.4 kernel** (d = 384, 16 blocks; `--clock-control none`, `--set full`):

| Measure | Value |
| --- | --- |
| Executed IPC per SM cycle | 1.89, of a maximum of 4 |
| Busiest pipe, integer ALU | 61.4% |
| Compute (SM) throughput | 55% |
| Thread instructions per modular multiplication, `add_mod` share included | 57.2 (matches SASS) |
| DRAM throughput | 720 GB/s, 46.3% of peak |
| L2 hit rate / L1 hit rate | 25% / about 0% |
| Registers per thread | 98, so 2 blocks per SM: 16 of 64 warps |
| Occupancy, theoretical / achieved | 25% / 23.1% |
| Eligible warps per scheduler per cycle | 0.90; 52.8% of cycles have none eligible |
| Cycles per issued instruction, per warp | 7.85, of which about 3.2 (40%) wait on a global load |

**Instruction mix of the loop** (`cuobjdump -sass`, sm_80): 915 instructions for 16 modular multiplications and 12 modular additions, plus 10 loads. Per multiplication: about 9 `IMAD.WIDE`, 18 on the IMAD pipe, 33 on the integer ALU (shifts, selects, compares, adds). Barrett needs about 5 emulated products plus conditional subtractions.

**Separating arithmetic from memory** (d = 384, ms; micro kernels in `core/bench/profile_search.cu`):

| Variant | ms | Note |
| --- | --- | --- |
| T0.4 reference | 29.60 | |
| Barrett arithmetic, operands in registers | 24.84 | no memory |
| Memory only, same loads | 17.12 | 1,129 GB/s |
| Memory only, 128-bit loads | 16.33 | 1,184 GB/s |
| Modular multiply only, Barrett | 22.29 | 2.17e11 per s |
| Modular multiply only, Montgomery | 13.62 | 3.55e11 per s |

The kernel's 29.6 ms is roughly arithmetic (24.8) plus memory (17.1) minus a little overlap. Occupancy is too low to hide both.

**On bandwidth:** T0.7's 18% to 21% describes the batched kernel when batching; its Q = 1 rows are 34% to 40%. The single-query T0.4 kernel measured here reads stored data at 37% to 42% of peak, and Nsight reports 46% DRAM throughput, as above.

## Result (A100)

Same harness before and after; identical inputs.

| Kernel | d | Before (ms) | After (ms) | Speedup |
| --- | --- | --- | --- | --- |
| T0.4 single query | 384 | 29.57 | 19.29 | 1.53x |
| T0.4 single query | 768 | 31.36 | 20.39 | 1.54x |
| T0.4 single query | 1536 | 33.30 | 22.42 | 1.49x |
| Batched, Q = 4 | 384 | 129.0 | 72.5 | 1.78x |
| Batched, Q = 4 | 768 | 133.1 | 75.2 | 1.77x |
| Batched, Q = 4 | 1536 | 141.8 | 80.9 | 1.75x |
| Ciphertext x plaintext | 384 | 14.39 | 11.97 | 1.20x |
| Ciphertext x plaintext | 768 | 15.16 | 12.55 | 1.21x |
| Ciphertext x plaintext | 1536 | 16.86 | 13.45 | 1.25x |

The T0.4 kernel's vectors per second after: 2.72e7, 1.29e7 and 5.85e6 at d = 384, 768 and 1536, and 2.5e11 modular multiplications per second at d = 384 (1.63e11 before). Instructions per modular multiplication in the loop, `add_mod` share included: T0.4 57.2 before, 42.7 after; batched about 35.7 after; ciphertext x plaintext 43 after.

Montgomery alone gave 24.6 / 26.9 / 27.0 ms, because the compiler used 96 registers (2 blocks per SM). `__launch_bounds__(256, 4)` limits the kernel to 64 registers with no spills, which gives the table above; the batched kernel uses `(256, 2)`, with 128 registers and 48 bytes of spill.

**How it stays exact:** the kernels accumulate `sum_j mont_mul(x_j, y_j)`, with every addition reduced, then multiply once by R (`mont_finish`). Inputs and outputs remain standard-form residues; no data is stored in Montgomery form, so the query needs no conversion on any path. The exactness argument is in `core/kernels/modarith.cuh`. Moduli must be odd, which RNS primes are; the search hosts reject even ones.

## Candidates dropped

| Candidate | d = 384 / 768 / 1536 (ms) | Why dropped |
| --- | --- | --- |
| Lazy 128-bit accumulate, flush every 8 dims, tile 4 | 21.4 / 22.0 / 22.8 (Montgomery 20.2 / 21.1 / 23.0 in that run) | 126 registers, 2 blocks per SM: no better than Montgomery. Exact, and safe for moduli up to 60 bits. |
| Lazy, tile 2, 2-word loads | 20.3 / 20.5 / 20.6 | Gains at most about 10%, at d = 1536 only, for 126 registers and more code. |
| Wider loads (2 words per thread) | Montgomery 20.0 to 21.2 at d = 384 (worse) | Memory-only gains 5%, Barrett 4%; registers double and occupancy halves on Montgomery. |
| Smaller tile | Memory-only: tile 2 20.4, tile 1 27.1 (tile 4 is 17.1) at d = 384 | Less stored-data reuse. |

## Limits

- Exact OpenFHE comparison: at the existing small sizes through `make test-gpu`, and up to d = 1536 through the search-sum stage of `tests/test_gpu_relin_rescale_mask.py` with `--expansion-large`.
- `__launch_bounds__` is a compiler hint tuned on the A100; its speed on the A10 was not measured.
- The Nsight run used 16 blocks rather than 64, to keep replay passes short.
