# T2.1 parallel client decrypt and top-k

Date 2026-11-09. Benchmark: `modal run modal_app.py::bench_topk` (`core/bench/topk_parallel.py`).
25 synthetic level-2 blocks, preset `m0_depth2` (8192 slots per block, last block 5461 valid), k = 10,
median of 5 runs after a warmup, CPU only. Each run is deserialize + decrypt + per-block top-k + merge.

**Host:** Modal CPU container (gVisor), `os.cpu_count()` = 32, affinity = 32. The sandbox hides the
CPU model: `/proc/cpuinfo` has no `model name` line, so the model cannot be recorded. The host is
shared and noisy (the serial time varied between 0.18 s and 0.32 s across runs).

## Results (two runs)

| Path | Run 1 | Run 2 |
| --- | --- | --- |
| serial | 0.178 s | 0.319 s |
| pool of 4 workers | 0.049 s (3.6x) | 0.088 s (3.6x) |
| pool of 8 workers | 0.029 s (6.2x) | 0.051 s (6.2x) |
| pool of 16 workers | 0.018 s (9.9x) | 0.027 s (11.9x) |
| pool of 32 workers | 0.028 s (6.3x) | 0.016 s (20.2x) |
| new pool forked on every call | 0.555 s (0.32x) | 0.386 s (0.83x) |

## Design and findings

- Forked worker processes (`fork` start method): they inherit the context and the secret key from
  memory. Nothing secret goes through pickle, arguments or disk; only the block path and index go
  in, and at most k (score, index) pairs come out. Fork after OpenFHE initialisation works: no hang
  or crash, including after the parent used OpenMP in key generation and encryption.
- Threads were not tried: processes already reach the target and keep the GIL question out.
- The speedup needs a **persistent pool** (`ParallelTopk`, created once per client). Forking a
  fresh pool for every query costs 0.3 to 0.5 s, more than the serial work itself (about 7 to
  13 ms per block), so the one-shot `parallel_topk` helper is slower than serial at 25 blocks. The
  client should create the pool at start-up. The workers hold the secret key in their memory for the
  pool's lifetime.
- Determinism: OpenFHE CKKS decryption adds fresh noise on every call, so decrypting the same
  ciphertext twice gives slightly different values. Two scores that are exactly equal in truth can
  therefore swap places between any two decryptions, in any path. Both paths use the same order
  (score descending, index ascending), so the results are identical whenever the true scores differ by
  more than the noise; the test uses scores 1e-3 apart and checks the order rule itself on exact ties.
- `e2e.py` stage 2 was not switched: it would need a persistent pool and a restructure of the
  harness around the server process.
