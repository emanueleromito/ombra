# T2.7: filter evaluation within depth 2 (decision 0019 measurements)

- **Command:** `modal run modal_app.py::bench --task t2.7` (A100-40GB, both presets). Raw JSON: `t2.7-m0_depth2-a100.json`, `t2.7-m0_compact_n8192-a100.json` (this folder). Code: `core/bench/filter_0019.py`; end-to-end through the gRPC server (`ombra_server`) and `tests/e2e_client.py`.
- **Data:** synthetic only (unit-norm random vectors; a Gaussian mixture of 16,000 vectors at d = 128 in 8 k-means clusters). Aggregates only. The latency is client wall time over localhost gRPC and includes Python decryption; it is not comparable with the server-only numbers of T1.3 and T2.2.
- **Method:** see the script header. lambda = 4; F_max asked from the server (14 at `m0_depth2`, 16 at compact, matching the formula).

## Reading against decision 0019

1. **Error against the band gap:** passes. Worst error 9.3e-8 (`m0_depth2`, F = 14) and 2.8e-5 (compact, F = 16) against a band gap of about 3.6 (2 guaranteed); no vector was misclassified; the added error on the true score is 11x and 7.9x at F_max.
2. **0012 recall rule with the extra columns:** passes in both presets and both variants on this dataset (gap at most 0.0001 against 0.005).
3. **Filtered recall:** recall@10 is 1.000 in every case except a filter at 50% selectivity that is correlated with the clusters: 0.954 with the default max_probe and 0.926 with max_probe 4. The cause is the stopping rule, not the encryption: the loop stops as soon as k matches are found in the clusters probed, and with a correlated filter those matches need not be the best matches overall. At 1% and 10% selectivity the loop needed 1.0 to 1.3 extra rounds when correlated, 0 when independent; Strict fallback fired for 44% to 58% of correlated queries at max_probe 4 and never at 8. No answer was incomplete.

## Limits

- One synthetic dataset, 8 clusters, d = 128, 50 queries per cell for Part 3 (a cell is noisy to about +-0.04 in recall). The 0012 rule asks for two real datasets; this is not that acceptance.
- Part 3 has no plaintext-filtered baseline with the same pruning, so the 0.926 to 0.954 cannot be split into the pruning's own loss and any other loss; Part 2 shows no encrypted-versus-plaintext gap, which points to pruning.
- A client that wants more recall for correlated filters can set a minimum number of clusters to probe (cost: latency) or continue past k matches; this is client policy for M3.
- Part 1 uses cardinality 4 and 3 queries; F_max fields with larger cardinality add columns (D grows) but not matches per field.
- A100 only; the Modal CPU model and the host differ from earlier results, so compare ratios, not absolute latencies.
