## Conclusion

**Recommendation: reject as a replacement for `m0_depth2` (decision 0014, proposed).** The candidate is exact, secure and 107x to 218x more accurate in score error, but it is not faster where it counts. Search throughput is the same within run-to-run noise (it is bound by memory bandwidth, and the stored bytes per vector are the same), while expansion is 2.09x slower and the automorphism keys are 2.0x larger, because 6 towers need twice the key-switching work and 32-bit words were used only in the search kernel.

## Candidate parameter set `m1_composite_n16384`

| Field | Value |
| --- | --- |
| Security level | `HEStd_128_classic`, ring dimension 16384 |
| Multiplicative depth | 2 |
| Scaling | `COMPOSITESCALINGMANUAL`, composite degree 2, register word size 32 |
| Scaling modulus size / first modulus size | 58 / 62 bits |

| Towers | 10: Q = 6 (bits 31, 31, 29, 29, 29, 29), P = 4 (31 bits each) |

| Largest prime | below 2^31, so a sum of two residues fits 32 bits |

`COMPOSITESCALINGAUTO` is not needed; `MANUAL` takes the composite degree from the preset. `m0_depth2` and `m0_compact_n8192` are unchanged (a test pins `m0_depth2`).

## Metadata under composite scaling (OpenFHE v1.6.1, measured and read from source)

- A rescale drops `compositeDegree` = 2 towers: level +2, noise-scale degree -1 (`ModReduceInternalInPlace`, `ckksrns-leveledshe.cpp:188`). A ciphertext goes 6 towers (level 0), 4 towers (level 2), 2 towers (level 4).
- The scaling factor is not 2^58: at level 0 it is 2.8796655456383795e17 (2^58 = 2.8823037615171174e17, 0.09% apart). Each rescale divides the tracked factor by the dropped primes one after the other; the GPU path does the same divisions in the same order and the oracle compares the factor exactly. Decode divides by the ciphertext's own factor, so a client that assumed 2^58 would be wrong by 0.09%.
- **Public `CryptoContext::Rescale` does nothing under `COMPOSITESCALINGMANUAL`** (`rns-leveledshe.cpp:352` acts only for `FIXEDMANUAL`). The rescale of the score happens inside `EvalMult(score, mask)`. The oracle for our explicit rescale is `scheme->ModReduceInternal(ct, compositeDegree)` (the call EvalMult itself makes), used in `ombra_search_gpu.cpp`. A user of the Python API cannot rescale explicitly.
- Level budget holds unchanged: expansion 0 levels, query x stored 1 (2 towers), mask 1 (2 towers), total 2. The mask must be encrypted at level 2 (`compositeDegree`), not 1. The client's 2^-L pre-scaling is untouched. Stored x query and score x mask are both degree 1 at the same level, so `EvalMult` takes its no-adjustment path.

## Exactness (hard rule 3)

All on the A10, comparing every RNS word, the moduli, level, noise-scale degree and scaling factor with OpenFHE: query expansion (the composite preset runs the existing expansion oracle), the 32-bit search kernel (sum of d products), relinearize at both levels, the 2-step composite rescale at both levels, the mask multiply with relinearization, and the whole GPU-only pipeline stage by stage, d = 16, 384, 768, 1536 for the pipeline; the search-kernel oracle runs d = 16 and 4 with 1 and 5 blocks. All PASS. The composite rescale is two single-tower rescales in a row on the device (`GpuCtOps::rescale_raw`), which is what OpenFHE's loop does.

## What changed and what stayed 64-bit

- **32-bit:** the search kernel only (`core/kernels/column_search32.cu`, native 32 x 32 -> 64 multiplication, Montgomery with R = 2^32). Stored and query words are held as 4-byte words on the device (chosen automatically when every modulus is below 2^31, so the 64-bit presets take the old kernel with identical behaviour); the result is written as 64-bit words.
- **64-bit words holding ~30-bit residues:** expansion (NTT, key switching, automorphism), relinearization, rescale, tensor product for the mask, and the key material. Expansion time below is therefore an honest number for "6 towers on 64-bit words", not for a native 32-bit pipeline.
- The batched search kernel (T0.7) and the plaintext search (T0.11) have no 32-bit path.

## Measure 1: search throughput (A100, T0.4 harness, same for both presets)

Kernel only, median of 10 runs after 2 warm-ups, 19.3 GB of stored data (blocks 64, 32, 16), relinearize and rescale excluded.

| d | `m0_depth2` ms (median / min) | candidate ms (median / min) | `m0_depth2` vectors/s | candidate vectors/s | Ratio (medians) |
| --- | --- | --- | --- | --- | --- |
| 384 | 24.39 / 20.01 | 22.26 / 21.76 | 2.150e7 | 2.355e7 | 1.10x |
| 768 | 22.91 / 22.90 | 21.95 / 21.93 | 1.144e7 | 1.194e7 | 1.04x |
| 1536 | 22.82 / 22.77 | 22.54 / 22.51 | 5.744e6 | 5.815e6 | 1.01x |

At d = 384 the `m0_depth2` run had a slow start (max equals median, min 20.01 ms); the minima give 0.92x. Read this as no difference. The two kernels read the same number of stored bytes (6 towers x 4 bytes against 3 towers x 8 bytes), and T1.4 found the 64-bit kernel already at 88% of the memory-only floor, so there is nothing left for cheaper arithmetic to win.

Launch-bounds sweep of the 32-bit kernel at d = 384 (minimum blocks per SM; registers 48 / 40 / below 40): 4: 23.93 ms median; 6: 20.67 ms; 8: 21.68 ms. Runs vary by about 10% between launches of the same binary, so the default (4) was kept; 6 looks slightly better and could be adopted with a repeat measurement.

## Limits

- Search throughput is the kernel alone. The total search (search, relinearize, rescale, mask, rescale) and the end-to-end latency were not re-measured for the candidate; its relinearize and rescale run on 64-bit words with 6 towers and would be slower than at `m0_depth2`.
- Only the expansion and the search kernels were benchmarked on the A100; the oracle tests ran on the A10. No recall run (T1.6 check) was done for the candidate.
- The 10% run-to-run spread means the ratios in measure 1 are not significant; the launch-bounds default was not tuned on repeated runs. The `m0_depth2` medians here (24.39, 22.91, 22.82 ms) are slower than T1.4's for the same kernel (19.29, 20.39, 22.42 ms), a different harness and run; only the before and after within one file should be compared.
- A native 32-bit expansion and key-switching path was not built; it could narrow the expansion gap but not remove the 2x work from 6 towers, and was out of scope.
- A client using Python alone cannot call an explicit rescale under this scaling mode (see above); the product would need a C++ path or `COMPOSITESCALINGAUTO` semantics.
