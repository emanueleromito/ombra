# T0.11 step 3: seeded encryption (write-up only)

No implementation. Read from OpenFHE v1.6.1 at the pinned tag.

## Idea

With secret-key encryption, a ciphertext is `(c0, c1)` with `c1 = -a`, where `a` is uniformly random. If `a` could be regenerated from a short seed, the server would store only `c0` and a seed, halving encrypted-DB storage: about 48 bytes per dimension per vector instead of 96 (`2026-11-09-t0.9-sizes.md`), the same as plaintext-DB RNS storage.

## What OpenFHE provides

- **No seeded or compact ciphertext form.** Nothing in `pke/` exposes one. `CryptoContext::Compress` (`cryptocontext.h:2730`) does something else: it reduces the modulus by dropping towers, which shrinks a final result for download, not stored data that still has to be multiplied.
- **Secret-key encryption exists:** `PKERNS::EncryptZeroCore(privateKey, ...)` (`rns-pke.cpp:115`) computes `c0 = a * s + ns * e`, `c1 = -a`, with `a` drawn directly in evaluation form: `DCRTPoly a(dug, elementParams, Format::EVALUATION)` (`rns-pke.cpp:126`). Each tower is sampled independently (`dcrtpoly-impl.h:168-173`).
- **Public-key encryption cannot be seeded this way:** Ombra uses it today (tests and T0.8), and there `c1` is derived from the public key, not uniform. Seeded storage would mean encrypting the database with the secret key on the client, which the client can do.
- **The generator:** `DiscreteUniformGeneratorImpl::GenerateVector` (`discreteuniformgenerator-impl.h:97`) uses `PseudoRandomNumberGenerator::GetPRNG()`, which by default is `Blake2Engine`: a 512-bit seed and a counter, where each block is `blake2xb(key = seed, input = counter)`, so the same seed and counter reproduce the stream (`blake2engine.h:65-72`). External engines are supported through a `createEngineInstance` plug-in (`prng.h:60`).

## What reproducing it on the GPU would take

1. **A seed per ciphertext.** OpenFHE seeds its generator globally and exposes no per-ciphertext seed in `Encrypt`, so this needs either a custom PRNG engine plug-in that reseeds per ciphertext, or a change to OpenFHE. The second conflicts with the pinned version.
2. **Exact reproduction of `a`.** The GPU would need Blake2xb in counter mode and OpenFHE's exact mapping from generator output to integers below each tower modulus, per tower, in the same order, so that the regenerated `a` matches word for word.
3. **A correctness test against OpenFHE** at the word level, like every other kernel.

## Conclusion

Possible in principle, and likely to work, but it touches hard rule 3 (encryption uses OpenFHE only) and may need a custom PRNG plug-in. The alternative, Ombra sampling `a` itself and computing `c0` outside OpenFHE, breaks hard rule 3 outright, because Ombra would be implementing encryption. **This needs its own decision before any work**, weighing a 2x encrypted-DB storage saving against that risk. Unique seeds per ciphertext would be a security requirement of any version.
