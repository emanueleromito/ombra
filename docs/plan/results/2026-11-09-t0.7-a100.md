# T0.7: query batching

- **Command:** `make bench TASK=t0.7` then `make results-pull`
- **Commit:** `fa1e653`
- **GPU:** NVIDIA A100-SXM4-40GB (`clocks.max.memory` 1215 MHz, `memory.total` 40960 MiB; 42,429,251,584 bytes reported by CUDA)
- **CUDA:** 12.6.3 image. Compiled for sm_80 and sm_86.
- **OpenFHE:** v1.6.1 (pinned image)
- **Parameter set:** `m0_depth2` from `core/params/ckks_presets.json`, unchanged: HEStd_128_classic, ring dimension 16384, depth 2, scaling 50 bits, first modulus 60 bits, batch size 8192, FIXEDMANUAL, HYBRID (decision 0009)
- **Timing:** median of 10 runs after 2 warm-up runs, Release build, wall clock over all passes. Excludes relinearization and rescale (as in T0.4).
- **Raw output:** `docs/plan/results/raw/results/t0.7-a100.json` (gitignored)

Oracle tests (`make test-gpu`, A10, 20 passed): batched search matches OpenFHE exactly at d = 16 with 1 block and d = 4 with 5 blocks, for Q = 1, 3, 8. Batched expansion matches exactly at d = 13, 16, for Q = 1, 3, 8. Decrypted errors within 1e-6.

## Key finding

**Batching gives little throughput on this hardware.** Both workloads are limited by compute, not by launches or memory traffic:

- **Search:** 1.2x to 1.54x against the same batched kernel with Q = 1. Against the single-query T0.4 kernel, batching is roughly a wash: 0.93x at d = 384, 0.97x at d = 768, 1.03x at d = 1536 (see the comparison below). The kernel sustains about 1.5e11 modular multiplications per second at every Q.
- **Expansion:** 1.01x to 1.05x. T0.5b already fills each tree level with enough work to occupy the GPU, so merging trees adds nothing.

Decision 0007 names batching as the main throughput lever. These numbers do not support that for the search and expansion kernels at `m0_depth2` on one A100.

The Q = 1 search rows are noisier than the others: individual runs split into about 9.7 ms and 12.1 ms, and the median can land on either. The speedups over Q = 1 carry that uncertainty.

## Memory limits

128 queries do not fit in one pass. At the 34 GiB budget, up to 97, 50 and 25 queries fit per search pass (d = 384, 768, 1536), and up to 46, 23 and 11 per expansion pass. Larger Q runs as consecutive passes, and the time for all Q is what is reported. One pass per Q holds the query data, the results and the working state on the device at once.

`cudaMalloc` rounds each small allocation up: 786,432 bytes became 1,048,576 on the A10 (`ombra_mem_probe`). The first A100 run ran out of memory for this reason. Expansion ciphertexts now live in 256 MiB slabs; the A100 run reports a footprint of 787,201 bytes per ciphertext, within 0.1% of nominal.
